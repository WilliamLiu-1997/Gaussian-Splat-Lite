# Architecture

[Back to documentation](../README.md#documentation)

This guide is for contributors. It describes internal module boundaries, backend differences, and resource lifetimes. To use the library, start from the [README](../README.md#quick-start) and the API pages it lists; those pages describe behavior, and this one explains how it is implemented.

[`src/index.js`](../src/index.js) defines the runtime exports, and [`src/index.d.ts`](../src/index.d.ts) defines the public type exports. Implementations use JavaScript with adjacent `.d.ts` files; modules containing only types need no JavaScript file. Applications use `SplatMesh` for models and one `GaussianSplatRenderer` for the scene.

## Rendering boundaries

The renderer combines visible models using Three.js transforms, visibility, and layers. Initialize `WebGPURenderer` before creating `GaussianSplatRenderer`: the renderer type selects the material API, while its actual backend selects compute/storage or raster/textures.

| Owner | Responsibility |
| --- | --- |
| `GaussianSplatRenderer` | Scene updates, accumulator handoff, and sorting |
| `SplatCapture` | Independent capture Splat state, offscreen targets, readback, and PMREM |
| `SplatAccumulator` | Scene mappings, versions, camera-relative origin, and WebGL texture generation |
| WebGPU backend | Compute projection, caches, GPU sorting, and indirect drawing |
| WebGL backend | GLSL materials, ordering textures, and texture generation |
| WebGL fallback backend | Raster generation and CPU-sorted ordering textures |
| Shared TSL code | Generation and projection math, materials, and color conversion |

For sorted rendering, native WebGPU keeps ordering and visible counts on the GPU and sorts before drawing; its accumulator carries mappings and edit metadata without generating combined textures. Both WebGL backends use asynchronous Worker/WASM sorting and retain the previous display until a matching order is ready.

In `webgpu/`, `ProjectedSplats.js` coordinates projection and sorting, `ProjectionCache.js` owns projected storage, and `RadixSort.js` owns sort passes. WebXR uses the eyes' mean pose for generation and sorting, with separate projections for each eye. Both WebGL backends share `webgl/OrderingTexture.js` for allocation and disposal, while keeping their own upload and binding paths.

`backend.js` selects the backend from the renderer type and its public `coordinateSystem`, which distinguishes native WebGPU from WebGL fallback. It chooses the blend space for each output: the working color space by default, `renderer.outputColorSpace` when WebGLRenderer draws to the canvas, and the target texture's color space when it draws to an XR-style target.

Projected Splat support is capped at the viewport's short side, in projection space scaled by `focalAdjustment`, in both the TSL projection program and the GLSL vertex shader. The quad and its UV extent shrink by the same ratio, preserving the Gaussian profile.

A kernel still above `minAlpha` where its support ends is faded there instead of cut off. The fragment stage rescales it about its peak, `(alpha + fade) * kernel - fade`, so it reaches `minAlpha` at the support edge. The quad is never enlarged.

- **Gaussians.** Only `maxStdDev` can end a Gaussian early, so its fade follows from its alpha and the per-draw `edgeFade` uniform, a scale and offset derived from `maxStdDev` and `minAlpha`. It needs no per-Splat data, and a Gaussian that `minAlpha` already ends is drawn exactly as before.
- **Wide kernels.** The edge value depends on the kernel power, so the projection computes the fade and stores it as a half in the low 16 bits of the squared support radius. That radius is first rounded down to its high 16 bits, at most 0.6% of the radius, which keeps the fragment stage's radius test exact. The squared radius therefore passes to the fragment stage bit for bit, and native WebGPU caches it in place of the radius.

Errors from automatic updates are caught and logged once per message; a draw whose preparation fails is skipped. Explicit `update()` calls rethrow to the caller. `frameCallbacks` is an internal flag for a second renderer on the same scene, so each `SplatMesh.onFrame` runs once per frame.

Resource rules:

- Wait for outstanding GPU compilation before disposing the sorter; preserve compute nodes when resizing resources or changing source meshes.
- Keep color conversion and XR output handling with the backend that owns them.

### Stochastic rendering

Sorted and stochastic draws compile separate shaders without mode branches. A mode change takes effect at the next update boundary, after the current draw; both WebGL backends also wait for the matching accumulator and sort, and `stochasticActive` reports the mode being drawn. Stochastic draws use the opaque list with depth testing and writing.

Coverage uses a tileable 32-frame spatiotemporal blue-noise atlas (`blueNoise.js`, generated by `scripts/generate-blue-noise.js`) on all backends. Each Splat keeps its own spatial offset and temporal phase, so consecutive samples follow the atlas's time axis instead of choosing unrelated offsets. The temporal sequence is optimized for exponential history accumulation and wraps after 32 samples. `stochasticSample` advances once per scene render, and every view in that render shares it.

Seeds exist only for stochastic draws: WebGL accumulators omit the seed layer in sorted rendering, and native WebGPU allocates its seed buffer on demand. Front-to-back stochastic ordering uses 16-bit keys. With unsorted stochastic rendering, `shrinkResources()` releases the sort worker and ordering.

## Capture boundaries

[SplatCapture](SplatCapture.md) is optional; the core renderer allocates no capture resources.

- **Independent Splat state.** The helper owns an internal `GaussianSplatRenderer` with `autoUpdate` and stochastic rendering off, sharing the display renderer's timer, loaded Splat data, and model-owned SDF edit textures. Its accumulators, sorting, and projection resources are separate, so display ordering and camera state are untouched. Global and model-local edits apply to captures and follow their latest values. `frameCallbacks` is off, leaving `onFrame` to the display renderer.
- **Stencil captures.** 2D and cube targets follow the Three.js renderer's stencil setting, with no separate capture option; a 2D target without a depth buffer gets no stencil, since Three.js attaches stencil only with depth. The intermediate target uses a depth-stencil attachment when stencil is enabled. With stencil, intermediate depth is 32-bit float for a float output depth texture or a default attachment with reversed depth; otherwise it is 24-bit. The scene's stencil masking applies before copying its color and depth to the output.
- **Options.** Quality, sorting, and material options are copied from the supplied renderer at the start of each capture. The active Splat material's stencil comparison and write settings are copied as well. Cube captures force radial sorting. The internal renderer takes the capture camera's layer mask.
- **Two phases.** Preparation awaits `update()` on the original scene with an explicit set of excluded objects. Collection skips models under those objects without changing visibility, while global edits follow the original scene's visibility. If the display updates shared models during a pending sort, preparation runs again with the same exclusions; appearance-only changes reuse the ordering. The draw is synchronous: other Splat renderers' layer masks are cleared, `hideObjects` are hidden, and the internal renderer joins the scene. `withCaptureState()` saves and restores the render target, cube face, mip level, XR setting, automatic clearing, and MRT. Nothing stays changed across an `await`, and everything is restored when drawing throws.
- **Ordering.** Captures on one helper are queued and run in call order. The camera or `worldCenter` is copied when the call is made. `renderReadTarget()` and `renderEnvMap()` read or filter inside the same queued task, before a later capture can redraw the target.
- **Cube captures.** Splat data is prepared at `worldCenter` with a 90° camera, then six faces render with automatic updates off. Both WebGL backends share one radial CPU sort across the faces; native WebGPU projects, compacts, and sorts for each face while drawing. Every capture runs `update()`, whose version checks reuse valid data and ordering, so 1.1.8's `update` option is not offered. Mipmaps are generated after the sixth face. Filtered and unfiltered cubes use separate targets, reallocated when size, clipping planes, or the renderer's stencil setting change.
- **Color.** `WebGLCapture` renders into an intermediate flagged as an XR-style target, 8-bit unless the output is float, so materials convert to the output color space before blending as on the canvas; a full-screen pass then converts to the target's storage space and copies depth. `WebGPUCapture` renders in the working color space, then applies the renderer's output transform and converts to storage space. On both, float outputs keep their type so values stay unclamped, and the intermediate takes the output's sample count, so multisampling applies to the scene and not to the final pass.
- **Readback.** `pixels.js` returns packed RGBA8 with the bottom row first on every backend, flipping native WebGPU's top-left origin. Three.js returns tightly packed rows. Supersampled targets are box-filtered on the CPU. Cube faces are normalized to the WebGL cube render target layout: native WebGPU stores +X and −X swapped and reads each face rotated 180°.
- **Ownership.** `dispose()` releases the internal renderer, 2D and cube targets, readback buffers, and the PMREM generator. Each texture from `renderEnvMap()` belongs to the caller; disposing it also releases its PMREM render target.

## Temporal anti-aliasing boundaries

[TAAPass and TAANode](TAAPass.md) are derived from Three.js TRAA, without a velocity attachment: reprojection uses scene depth and camera motion only, so object motion is not tracked.

- `taaShared.js` owns the state both share: a 32-entry Halton(2, 3) jitter sequence, jittered and unjittered projections, previous-frame matrices, the history index, sizing, and reset. It supports custom projections, scaled rigs, reversed depth, and logarithmic depth.
- Each implementation captures the scene itself into a half-float target with a depth texture and resolves between two history targets, with no history copies. The resolve applies depth rejection away from edges, neighborhood clipping, and luminance-aware blending.
- The capture target takes a stencil buffer when the Three.js renderer has one; the history targets never do, since the resolve writes only color and depth. Depth stays 32-bit float on every backend.
- The camera's projection is jittered only during capture. Native Splat projection reads the unjittered matrix through `getTAAProjection()`, so projection and sorting results are reused while only the jitter changes.
- `TAAPass` flags its capture target as an XR-style target, so Three.js converts materials to `renderer.outputColorSpace` before blending, matching canvas blending. Tone mapping is disabled during capture. The final copy decodes the sRGB transfer into the composer's working-space buffer, the inverse of `OutputPass`, so the two round-trip at any alpha; as the last pass it presents the output-space image unchanged. An output color space change resets history.
- `TAANode` is a TSL node updated once per render. It captures and accumulates in `ColorManagement.workingColorSpace`, leaving tone mapping and output conversion to `RenderPipeline`. A working color space change resets history.

## Neural denoiser boundaries

[NeuralDenoiseNode](NeuralDenoiseNode.md) follows Hu et al., "Ultra-fast Neural Inference for Stochastic Gaussian Splatting Denoising" (arXiv 2609.25604), in its form without per-Gaussian parameters. The authors published no code or weights; the two models in `neuralDenoiseWeights.js`, of 655 and 1,894 parameters, were trained on this renderer's stochastic frames, with a moving camera and moving objects.

- **Structure.** Two running means per pixel: an accumulated path over raw frames, which converges to the blended image, and a denoised path over spatially filtered frames, which covers short histories. One small network predicts how far to trust each path's reprojected history. A gate mixes the paths by the accumulated path's history length and the standard error of its mean, and a stabilization pass blends the result with the previous image inside the range of the current 3x3 neighbourhood.
- **Departures from the paper,** each for content that moves without motion vectors. Reprojection uses the third nearest depth of the 3x3 neighbourhood, because stochastic depth is the depth of whichever layer survived and jumps between layers. A slow low-pass luma, accumulated with the accumulated path's weights, feeds the network: against the current filtered frame it shows slow motion that single noisy frames hide. The difference between the two is also kept per block, with its sign, as running means over about 3, 6, 12 and 24 frames (see Still views below). Four inputs compare chroma: every other cue is a luma difference or a depth mismatch, so a translucent tinted object that writes no depth changed neither and left its tint in the accumulated path. The stabilization blend, the accumulated path's share of the gate and the spatial filter's strength are predicted rather than fixed. The trust network runs on 4x4 blocks and its output is upsampled.
- **Reprojection.** Both profiles align history from the camera matrices and the view depth. Object motion is handled by rejecting stale history, not by estimating a screen-space shift. The former image-motion fit, its 49-parameter decision network, eight passes and motion textures have been removed. The remaining profile 2 weights are unchanged; its learned frame filter and pixel correction remain. Existing training checkpoints that include following must be evaluated with `FOLLOW = False` to match this runtime.
- **Profiles.** `"profile1"` uses the eight-channel trust network with the fixed kernel (see Lean pipeline). `"profile2"` adds a learned filter for each frame (see Learned filter) and a correction of the block decisions per pixel (see Pixel decisions): 1,894 parameters. Both run one pipeline with camera-only reprojection. Their relative strengths depend on the scene, motion and metric; the profile numbers do not rank image quality. During development there was a third level, `"quality"`, and it was removed: the larger network did not improve on `"profile2"` within one render of the scene at the image's size and without a coverage variant (see More samples). This earlier level is separate from the current four-sample coverage setting. It first ran a second, fuller pipeline with a larger model: sixteen hidden channels and one residual block between the network's two stages, on 2x2 blocks, with reprojection, update and stabilization as passes of their own over every pixel. Once `"profile2"` had the learned filter too, that level measured behind it almost everywhere for a quarter more frame time, and its source was removed. Neither thing that set it apart paid: 2x2 blocks give the network noisier statistics than 4x4 blocks, and capacity is not what limits the image. The larger network alone measured 0.1 to 0.5 dB better than the smaller one on moving content in the full pipeline and the same on still views, no better at all without following, and the same on every test set in the lean pipeline when trained as `"profile2"` was. What limits the image is the noise of one frame, the two paths, and what reprojection can align.
- **More samples (earlier experiments).** With motion, history is short, and the image is as noisy as the few frames it holds. How long to keep history is one curve, not a place to gain: pushing the trained trust up at inference lowers flicker and grain where something has just moved away and lengthens the trail by as much, pushing it down does the opposite, and the trained point is where PSNR under camera motion peaks. History itself is the limit while the camera moves. A converged image of the previous frame, brought to the current view with the model's own reprojection, is 33.9 dB from the current frame's where the surface is the same one, against 37.5 dB for two converged images of one view, and one resampling of a detailed image costs most of that; resampled once per frame, a history of eight frames has lost three tenths of its fine detail. On a model of 12 million Splats turning at 9 pixels per frame, the 42% of pixels with under four frames of accumulated history hold 80% of the squared error, and forcing trust up wherever a pixel's history is its own surface's does not lower it: that history is no better than the frame's filter. Ways to use history better therefore measured little or lost, weights unchanged: a wider network the same; the model's true motion in place of the estimate (an upper bound) 0.1 to 1.0 dB at the front; the last frames each reprojected once in place of a resampled history worse, since a frame eight frames old aligns to 29.5 dB; a filter guided by the previous image no better than the blend with it; and sharpening the result nothing. Two more measured little on those test sets and are in use since, for what they do on large scans and before empty backgrounds: a sharper kernel for the accumulated history (see History kernel) and a depth for empty pixels from what was drawn beside them (see Sparse blocks). What gained most was more samples of each pixel in a frame. Two ways to get them from one render were built and withdrawn at that stage. The following measurements belong to those earlier implementations, not the current coverage profiles. One draws the scene into a target with four coverage samples per pixel with a variant of the stochastic Splat material that tests coverage once per sample and writes a sample mask: of a pixel's four samples a fragment covers as many as the thresholds (k + r) / 4, k = 0 to 3, lie under its alpha, r being the random value the usual test compares alpha with. A frame is then 28.2 dB from the converged image where one sample gives 21.1 dB, both converge to the same image, and with the `"profile2"` weights unchanged the front of moving content gains 1.7 dB, what it has just left 1.4 dB with a quarter less flicker and a third less trail, camera motion 1.0 dB, and the worst still view flickers half as much, for 4 ms more per frame at 2560x1600. It needs that material variant in the Splat renderer, written through Three's WGSL builder because TSL has no output for a sample mask, and a plain multisampled target gains nothing since the usual test is per pixel; writing the mask from the usual material as well cost 6% of the scene's time at one sample. It was withdrawn to keep the renderer free of code that serves one addon. In a linear working color space its four samples were also averaged by the multisample resolve before the transfer, not after it as frames are over time, so partly transparent Splats came out brighter than at the other levels. The other draws the scene twice as wide and as tall with the usual material and averages 2x2: the same gain as four independent samples, no change to the renderer, and three times the cost (11 ms). Before both, a level that rendered the scene twice per frame cost the scene's whole time again.
- **Lean pipeline.** Measured pass by pass, the full pipeline without following spent a fifth of its time on the view depth, two fifths on two passes over every pixel with four half-float targets each (one reprojects, one updates), three tenths on the network at half resolution, and a tenth on stabilization. The lean pipeline, which both profiles run, keeps what the image is made of, both running means, the gate and stabilization, and takes the rest more coarsely. The view depth is kept per 2x2 block. The network runs on 4x4 blocks and takes a block's means directly: of the history from four bilinear taps into the previous frame's state at where the block was, so nothing reprojected is stored for it; of the frame from the image pyramid; of the filtered frame from thirteen bilinear taps into the pyramid, which give that mean exactly because the fixed kernel is linear, or from four taps into the learned filter's result where there is one. One pass per pixel then reprojects, filters, updates both paths, mixes them and stabilizes. Stabilizing in that pass means its tolerance cannot come from the current result's neighbourhood, which is not in a texture yet. It comes from what the previous image spans across the five taps it is resampled with, and on every test set the two measured the same. Against the same network in the full pipeline it adds half the time to a frame (see Cost), measures within 0.2 dB on every test set, and generally flickers less on still views, because a 4x4 block's statistics carry half the noise of a 2x2 block's: with following added and nothing else, the worst still sequence's 99.9th percentile is 0.0089 where the full pipeline's was 0.0126. What it loses is detail while the camera moves, about a tenth at `"profile1"`, since history is dropped a 4x4 block at a time. At `"profile2"` the pixel correction and the learned filter more than make up for it. The network has to be given the block's mean of the filtered frame, not only of the frame. The filter moves light across a block's border, so beside a thin bright edge the two differ for good. A first version compared a block's own colour with its filtered history, read that difference as lasting change, and a still view of such an edge flickered three times as much.
- **Pixel decisions.** At `"profile2"`, a 72-parameter pointwise network refines the block's trust in the two histories, the accumulated path's gate share and the spatial filter's strength using this pixel's current and historical luma/chroma differences and noise scale. It corrects their logits inside the existing resolve pass, without new textures, history or passes. Trained alone on the lean model with following, everything else frozen, it raised the amplitude of fine detail while the camera moves from 0.557 to 0.609 of the reference's (23 sequences, 198 reference frames, RGB after a 5x5 high-pass; the full pipeline measured 0.614) and halved the worst still view's flicker, from 0.0089 to 0.0046. It does nothing for the grain or the flicker of moving content. Its arithmetic per pixel costs 0.15 to 0.20 ms at 2560x1600, which is why `"profile1"` goes without it.
- **Learned filter.** At `"profile2"` a network of 1,167 parameters predicts a 3x3 kernel for every pixel, at three levels of the frame's image pyramid and then at full resolution, where it can also leave a single sample out (see Dots). Each level filters itself and decides per pixel how much of that to keep over the level below. A level's network sees its colour, the result from below, how far the four finer pixels of each of its pixels are from their mean (the noise at that scale), and the hidden channels of the level below. A kernel is nine weights that sum to one, so the filter only ever averages the frame: it cannot invent content, and since it reads nothing but the frame it cannot leave a trail. It was trained alone first, single frames against converged references (28.8 dB where the fixed kernel reaches 27.8 dB), then together with the trust network. Wider versions measured the same alone, and one of 80,000 parameters 0.4 dB more. In the full pipeline, against the same model with the fixed kernel, PSNR rises by 0.6 dB while the camera moves, 0.3 dB on still views and behind glass, and 0.2 dB on sequences with moving objects; where the image has just changed it measures the same. The image is cleaner rather than sharper: its fine detail has the same amplitude and follows the reference more closely (correlation 0.63 against 0.60). In the lean pipeline, where the filter came with training the whole model together, PSNR rises by 0.6 dB while the camera moves and 0.3 dB behind glass and in what a moving object has just left, which also flickers 15% less; fine detail under camera motion goes from 0.61 to 0.69 of the reference's amplitude, and its correlation from 0.58 to 0.63.
- **Dots.** One frame of stochastic Splats has sparse outliers: a bright wall that a few samples in a hundred pass through, a faint Splat before an empty background. History averages them away, and where a pixel has none they stand as dots, darker or brighter than what surrounds them: on a model of 12 million Splats, a white column showed about ten dark dots per frame while the view was dragged around it. Three things act on that. First, the learned filter's full-resolution kernel is predicted from half-resolution hidden channels, the same for the four pixels of a 2x2 block, so it could not tell which of them held the one sample that passed through a wall. Its network now also sees how far its own pixel is from the half-resolution result, and each of the nine taps loses weight with its own distance from that result, at a rate the network predicts per pixel: 31 more parameters, and trained alone on single frames a ninth of the bright dots at a slightly higher PSNR. Second, where the denoised history is under two frames and the camera changes the image fast, by the pixel's own motion or by the camera's turn swept over half the view, the denoised path takes a wider filter's result in place of the filtered frame: the learned filter's half-resolution result, or at `"profile1"` the frame's mean over 4x4 pixels. Third, most of what was left at a few pixels per frame was not missing history but another surface's: three in four of the dark dots sat on pixels that read their history from a place where the previous frame had kept a different depth, the background beside a column that had just moved on, or a rail in front of a wall. The network judges depth for a 4x4 block from one of its pixels, so a sliver of such pixels kept the block's trust. Each pixel now compares the depth its own surface had in the previous view with the depth kept for the 2x2 block it reads from; where they differ by more than a fifth, it drops both histories and its trust and takes the wider filter's result for that frame. The test follows the camera's speed, reading one half at a pixel per frame, and is void on a still view, where a pixel reads its own place and stochastic depth merely flips between the layers seen there. None of the three adds a texture or a pass. On that column, dark (bright) dots per frame of 768x480 at 4, 9, 17 and 35 pixels per frame went from 4.6 (141), 5.7 (190), 4.3 (133) and 7.6 (111) to 0.3 (10), 0.3 (6), 0.4 (1) and 0.4 (1) at `"profile2"`, and from 2.7 (3), 2.1 (9), 2.3 (12) and 1.3 (25) to 0.0 (5), 0.0 (1), 0.4 (1) and 0.0 (1) at `"profile1"`. The price is detail in motion: a view turning at tens of pixels per frame is softer while it turns (1 dB lower on such sequences), fine detail under ordinary camera motion has 0.64 of the reference's amplitude at `"profile2"` where it had 0.69 and 0.52 at `"profile1"` where it had 0.56, at the same PSNR, and the worst still view's flicker at `"profile2"` is 0.0027 where it was 0.0016. What did not work: training against dots with a loss on the worst pixels, which moved every other measure by 0.6 dB before it moved the dots; the wider filter wherever history is short at any camera speed, which costs 0.3 dB and a tenth of the detail because history is short everywhere while the camera moves; and the surface test without the wider filter, since the learned filter leaves a dark sample standing wherever history is dropped.
- **Wider comparisons.** With the learned filter, what the trust network compares has to be a statistic over about 4x4 pixels. The fixed kernel spreads every pixel over its neighbours, so even a 2x2 block's mean of the filtered frame was one. The learned filter keeps a thin edge thin and its noise with it: where a model's outline lies against the empty background, a different part of the outline's Splats is lit in every frame. A 2x2 block's filtered luma then moved half as much again from frame to frame, the network read that as change, and a still view of such an outline flickered four times as much. So in the full pipeline the filtered frame, the denoised history and the slow luma are compared as means over the 4x4 pixels around a block. Of fifteen still views fourteen then flicker less than with the fixed kernel, most by a third to a half. One flickers more, the far edge of a floor against the empty background (0.013 against 0.011), and training further on such views made it worse, not better. The lean pipeline's blocks are 4x4 to begin with, and there that view is still the worst of the fifteen, at 0.0027 (0.0016 before the changes against dots).
- **Coverage quality settings.** The fourth constructor argument, `samples`, selects 1 or 4 coverage samples independently of `"profile1"`/`"profile2"`. Sampling keeps the selected profile's network and pass count: twelve denoising passes for Profile 1, twenty for Profile 2. Quality 4x captures the scene once into a 4x multisampled half-float target. The Splat material factory can clone a stochastic material with different coverage, retaining its vertex graph and uniforms. During capture the addon substitutes that variant through the public `getRenderObjectFunction`/`setRenderObjectFunction` hook and restores the earlier hook in `finally`; the object's material is unchanged. The normal sorted and one-sample stochastic graphs do not write a sample mask. Only the variant's small output node calls `WGSLNodeBuilder.getBuiltin("sample_mask", ..., "output")`, the localized builder dependency required because r186 has no TSL sample-mask output. Nothing patches Three's builder or accesses its multisampled color attachment.
- **Coverage and resolve.** With the usual per-Splat STBN value `r`, quality coverage compares `fract(r + k / 4)` with alpha for each `k` from zero to three. Wrapping the phase makes every individual sample's coverage probability equal to alpha; fixed thresholds in disjoint strata assigned to fixed bits would bias overlapping layers. Each decision controls one bit of the four-sample mask. Samples are stratified, not independent full shading evaluations. Rasterizer coverage and per-sample depth/stencil further restrict the mask. Hardware resolves the four colors to their mean in the working color space. In a linear working space this precedes the display transfer, unlike the temporal averaging at the one-sample profiles; partly transparent Splats can therefore look brighter. The viewer's sRGB working space avoids that transfer difference. The denoiser reads multisampled depth directly and takes the nearest sample, respecting reversed depth, both for reprojection and for the optional single-sample public depth output. A pixel's mixed color still has only one representative depth. Multisampled color is discarded after resolve; depth is retained for these reads. Quality 4x adds about 44 bytes per pixel in scene attachments (32 color, 12 extra depth), for about 139 bytes per pixel total with Profile 1 or 160 with Profile 2 before stencil and the small viewport margin. This setting changes input sampling without retraining; it does not add object-motion following.
- **Noise period.** The renderer's coverage noise has 32 phases and the jitter 32 offsets, so a still view's frames repeat after 32 and their mean stops improving there: against the converged image it stays at 31 dB on a scan of 2.79 million Splats and at 36 dB on one of 12.2 million, however many frames are averaged. The noise is laid over the pixels of the target, so the node draws the scene into a target three pixels wider and taller than the image, through a viewport at one of nine places in it, another for every 32 frames, and its passes read the frame and its depth from there. The projection is the same at every place, so every sample stays where it was on the scene and only the part of the noise field a pixel meets changes: a frame is the frame of a renderer whose noise origin was moved, to the bit and to the border. The mean of 64 frames is then 3.1 dB closer than that of 32, of 96 frames 4.9 dB and of 128 frames 6.2 dB, which is what makes the accumulated path's 128 frames count: the models had been mixing a sixth to a third of the denoised path into a settled image because the accumulated one never got cleaner than 32 frames. It costs a copy of the frame in every working color space, where before only a linear one had its encoding pass, and a pass that copies the scene's depth into a texture of the image's size for `depthTexture`, which runs once an application has read that property (0.06 ms at 2560x1600). With the margin a frame took 0.1 ms longer at 2560x1600 and the same time at 2550x1590: presumably it adds a row and a column of the GPU's tiles where the image fills whole ones. The viewport must not be at the target's origin: Three sets none that is the same as the canvas's, and the scene would be stretched over the margin. The renderer is not changed for it. An earlier version moved the projection by a whole pixel and read the frame back moved the other way, which repeated a row or column at the border and offset `depthTexture` by up to a pixel and a half; a camera viewport, which would move the renderer's noise origin, cannot be used, because the renderer draws cameras with one only as WebXR eyes.
- **History kernel.** Reprojecting history once per frame gradually loses fine detail. All three full-resolution histories now use Lanczos-3 without its corner taps: nine bilinear taps, clamped to the range of the four pixels around the sample position so its negative lobes cannot ring over time. The accumulated path used this kernel already; the denoised path and previous displayed image now use it too. The displayed image still takes its stabilization tolerance from the five Catmull-Rom samples, matching the reference model. The three histories share one calculation of the sample position and kernel weights. This avoids repeating the sine evaluations and saves 0.8 ms at 1280x800 and 2.4 to 3.1 ms at 2560x1600 against the direct implementation on the measured hotel view; the extra texture reads still cost time compared with the earlier kernels. The change adds no parameters, textures or passes. Its benefit depends on the trained weights and was selected together with the detail loss below.
- **History length.** While the camera moves, a pixel reads its history between four pixels of the previous frame. Beside a place whose history was just dropped, that is a mix of a mean over a hundred frames and one raw sample, as noisy as the sample; its length, interpolated like any other value, came out near fifty, and the gate showed it as settled. Those were all the dots the accumulated path showed at a few pixels per frame, bright before an empty background and dark on a bright wall. The length is read through its reciprocal instead, from the four pixels themselves, so that the shortest decides, which is how the variance of a mix behaves; where the four agree nothing changes, and a still view is the same to the last digit. With the weights unchanged, dark (bright) dots per frame of 768x480 while the view turns about a white column at 4, 9 and 17 pixels per frame went from 0.6 (13.4), 0.9 (4.3) and 0.6 (0.7) to 0.1 (0.3), 0.3 (0.6) and 0.1 (0.0) at `"profile1"`, with PSNR under camera motion the same to 0.06 dB higher. The denoised history's length read the same way changed nothing.
- **Sparse blocks.** A 2x2 block where fewer than three of the nine pixels around it were drawn has no depth, and its history used to be read as if it lay on the far plane. That is right for an empty background and wrong for the soft rim of whatever stands before it. The rim of a thin branch, a few samples in a hundred, moved with the far plane while the branch moved by its own depth, so the rim's light was carried off into the background, where no frame draws over it and a mean over a hundred frames forgets it only slowly: a faint trail in empty space behind every thin edge, and a rim that broke up into grain. Three things act on that. First, such a block takes the depth of what was drawn around it: the mean disparity of the drawn pixels of the cell it lies in, from the narrowest of four cells, 8, 32, 128 and 512 pixels wide, that had at least eight pixels drawn. Four small passes sum those cells and the depth pass reads them. A rim then moves with its branch, and the empty space beside a model with the model. Where the drawn pixels do not agree on a depth (their disparities spread by more than 15% of their mean), as in haze at several distances, the block stays on the far plane: lent the mean of two depths, a thin pole before distant trees read its history beside itself and showed a gap. The lent depth is the block's depth in every comparison too, since a rim is the surface of its branch; with the far plane kept for comparisons, a rim's history was dropped whenever it was read from its own branch, and it stayed soft. Second, where to read is still a guess, so while the camera moves such a block keeps four frames of accumulated history. The displayed image also retains half as much of its previous value at full camera speed. Both reductions ramp with the camera's speed, leaving a still view unchanged. The earlier eight-frame limit already removed most of the long trail, but the display blend was still carrying the remainder into empty space. Third, at `"profile2"`, a frame of such a block is single bright samples before nothing, which the learned filter left standing as dots wherever the denoised history was short; there the denoised path takes the wider filter's result, as it does where history is short and the camera fast, at any speed. In the earlier borrowed-depth comparison, with the then-current weights unchanged, on three close views of bare trees before an empty background at 2 and 8 pixels per frame of orbit and 6 of sideways motion, the share of pixels brighter than 0.02 where the converged image is empty for four pixels around fell from 0.13% to 0.006% at `"profile1"` and from 0.26% to 0.012% at `"profile2"`; PSNR on those views rose by 0.8 to 2.8 dB and flicker over an area fell by a fifth to two fifths. Bright dots per frame while the view turns about a white column before haze, at 4, 9 and 17 pixels per frame, went from 11.1, 7.0 and 1.1 to 2.0, 3.6 and 0.3 at `"profile2"`. On scans that fill the view the change is between nothing and 0.4 dB for the better. Lending whatever was drawn nearest, however little, tripled the dots in haze from 9 pixels per frame up.
- **Rejected surfaces.** At `"profile2"`, only the share of the short-history fallback whose reprojected depth belongs to another surface is strengthened: half of that share takes the frame's existing 4x4 mean instead of the learned half-resolution result. Normal fast camera motion retains the learned fallback. Replacing every short-history fallback with the fixed mean lost 8% of fast-orbit detail on the elevator scan and was rejected. The localized change uses one additional read of an existing texture in the resolve; it adds no parameters, textures or passes. It strengthens filtering only where the reprojected history belongs to another surface.
- **Training target.** Motion is trained against the clean reference without blurring it, with weight 16 on the difference between the displayed and reference changes from frame to frame. The retained weights use an RGB detail term of weight 2 on moving sequences: the L1 error after subtracting a 7x7 mean from the RGB residual, using the same spatial weighting as the color loss. This penalizes lost detail and added noise; still sequences retain their existing convergence and flicker losses. The networks were trained for 900 steps from the previous weights. To balance motion detail and still stability, the profile 1 parameters average steps 600 and 900, and the profile 2 parameters average steps 300 and 600. Before the motion-following removal, each was evaluated with the three sharper history kernels; these are parameter averages, not extra inference passes. Against the previous weights and kernels, fine detail during camera motion rises by 4 to 6% at profile 1 and 7 to 8% at profile 2 over four scene groups and five camera motions. Grain rises by 3 to 6% and 6 to 8%, pixel flicker by less than 1.5%, while flicker over a 5x5 area stays the same or falls by up to 4%. Still views gain 0.13 and 0.20 dB. The initial motion-detail update increased isolated dots and some empty-background residue, and lost 0.17 and 0.14 dB behind glass. The subsequent sparse-history and rejected-surface cleanup kept the learned parameters unchanged; its measurements below predate removal of the following module. Earlier trials found that 188 extra training sequences alone changed measures by less than 0.1 dB, and a loss on isolated dots cost still views 0.3 to 0.6 dB, so it remains off.
- **After moving content.** Where something has moved across a settled surface, the pixels it covered start again from one sample once it has passed, and how the image looks there is set by the frames since: in the previous weights measured before large scans, twenty frames after content has left, the image was still 2.7 dB further from the converged one than where nothing passed, with a tenth less of the fine detail and a quarter more grain. Keeping the covered history aside and putting it back was measured on the reference in three forms and not adopted. Keyed by depth, it is triggered by stochastic depth, which jumps from frame to frame. Filled and read by the trust network's own decisions, with a check on depth and on the color of 4x4 blocks, it was grainier and 1 to 3 dB further some frames later. Holding a history without the frame, in place of dropping it, leaves standing the evidence that a block keeps changing, and a slow plain object leaves its own history held where the background should start again. With the clean references deciding what to put back, the wake gained 0.15 dB, because the networks as trained drop half of it at once: a store would have to be trained with them, and needs one more full-resolution texture.
- **Sizes.** Each level of the image pyramid takes the mean of 2x2 and leaves an odd last row or column out, so a pixel of any level covers whole pixels of the frame counted from the top-left corner. The pyramid is read at positions in pixels of the frame, matching the reference model. Stretching every level over the entire frame gives incorrect results at sizes such as 515x323.
- **Passes.** `NeuralDenoiseNode` is a TSL node like `TAANode` and reuses `taaShared.js` for jitter, sizing, stencil and reset. It captures the scene into a half-float target, then runs fragment passes written in WGSL (`neuralDenoiseShaders.js`, weights inlined as constants) directly on Three's `GPUDevice`, outside the node system, and exposes the last pass's target as its texture: twelve at `"profile1"`, two of them at full resolution (the copy of the frame and the pass that resolves it); twenty at `"profile2"`, three of them at full resolution, where the learned filter adds eight (one more level of the image pyramid, two passes at each of its three levels, and one at full resolution). Four of the passes are small: they sum what was drawn over cells of 8 to 512 pixels (see Sparse blocks). The copy of the frame takes the scene from where it was drawn in its target (see Noise period) and, in a working color space with a linear transfer, encodes it. No pass has more than four half-float attachments, the default limit.
- **Still views.** On strongly noisy content, such as a half-transparent bright layer over a dark one, one frame cannot tell slow motion from noise: a still block looks changed every few frames. A model that reacts to single frames keeps dropping the accumulated history there and shows the fallback, which flickers in patches; trained not to react, it smears slow motion instead. The running means of the signed difference separate the two, because noise changes sign and averages out while a change that lasts does not. They store the difference only, never image content, so reprojection under camera motion blurs noise away instead of inventing edges, and they fade with the trust of the history they describe. Training has to match: gradients run through time, since dropping a still pixel's history costs the frames after it rather than the frame at hand, and still views are held to zero change with the worst pixels counted separately.
- **State.** Kept from frame to frame in pairs that alternate between read and write: both means, one texture with the second moment of luma, both history lengths and the slow luma, the predicted trust and the evidence means at a quarter of the resolution, the view depth at half with a mark on blocks that have none of their own, and the displayed image. With the scratch textures of one frame that is about 95 bytes per pixel at `"profile1"` and 116 at `"profile2"` (21 of them the learned filter's scratch), in any working color space, against 36 for `TAANode`. Four coverage samples add the multisampled scene attachments described above, for about 139 bytes per pixel at `"profile1"` or 160 at `"profile2"`.
- **Half-float rounding.** Metal truncates a float written to a half-float target. A 128-frame running mean then loses half a unit in the last place on every write and ran 3% dark after 200 frames. At start the node draws a value between two halves and reads back which one was stored; where the GPU truncates, every pass adds half a unit before writing.
- **Color.** The networks were trained on display-referred values. In a working color space with a linear transfer, the pass that copies the frame also encodes it with the sRGB transfer (on the unpremultiplied color) and the output node decodes it, so partly transparent Splats resolve on display values in every working space. A working color space change resets history.
- **Validation after motion-following removal.** The remaining weights are unchanged, and generated shader logic matches the previous implementation with following disabled. Chrome 154 ran both profiles through still views, rotating Splats, reset and resizing without errors. GPU allocation counts are 12 / 20 denoising passes, excluding scene rendering and final presentation, and about 95 / 116 bytes per output pixel including the scene target, history and scratch textures. Five frame-by-frame comparisons cover 72 moving-mesh frames at both profiles and, at profile 2, 72 slow-orbit frames at 515x323, 48 fast-orbit frames and 40 thin-branch frames. Against the PyTorch reference with profile 2 following disabled, the largest per-frame mean absolute difference is 0.00043 for the displayed image and 0.00033 for accumulated history. These are frame means, not maximum pixel errors. Removing the unused motion-only jitter uniform and repacking the uniform block to 64 floats left all five captured state streams byte-identical. This verifies the removal and parity; the full quality suite and frame-time benchmarks below have not been rerun for the new profile 2 pipeline.
- **Historical cost before motion-following removal.** These timings include the former profile 2 motion estimator and are not timings of the current profile 2 pipeline. On an Apple M5 Pro with Chrome 154.0.8037.98, complete GPU frames at 1280x800 and 2560x1600 measured P50 / P95 on the 986,312-Splat example in a linear working color space: TAANode 3.60 / 4.15 ms and 7.25 / 7.80 ms; profile 1 4.60 / 5.20 ms and 11.15 / 11.55 ms; profile 2 5.00 / 5.60 ms and 12.25 / 12.65 ms. On the 12.2-million-Splat hotel in sRGB, profile 1 measured 17.80 / 19.05 ms and 24.65 / 25.30 ms; profile 2 18.20 / 19.55 ms and 25.75 / 26.35 ms. It adds no textures or passes, but the extra arithmetic and texture read still have a measured cost. Costs vary with device, image size and view; two-run P95 is not a general bound. A loop over texels must not branch on what it reads: an earlier depth-cell sum took 1 ms at the larger size with a branch and 0.1 ms with select.
- **Historical validation before motion-following removal.** The following quality and parity results describe the preceding implementation, including its profile 2 motion estimator; they do not establish the current profile 2 quality. Across all eight comparisons, the largest per-frame mean absolute difference is 0.00043 for the displayed image, 0.00035 for accumulated history and 0.00147 pixels for the motion estimate. These are frame means, not bounds on individual pixels. ## Decoder boundaries

PLY, SPZ, SOG, and RAD decode in `gaussian-splat-lib` and publish through `SplatReceiver`. This core library has no JavaScript or WASM dependency. `gaussian-splat-rs` adapts browser inputs and writes the output into JS typed arrays through `SplatsData`.

- PLY/SPZ consume byte streams through `ChunkReceiver`.
- SOG decodes property-image groups into bounded batches. Metadata, ZIP validation, images, and SH palettes belong to the core decoder; `SogDecodeSession` bridges that API to JavaScript.
- RAD retains dataset codebooks between page requests and returns packed records with separate tree metadata.

[`loadSplatData`](../src/loaders/loadSplatData.js) coordinates decoding, resolvers, cancellation, progress, and loading-manager callbacks, returning packed `SplatResult` data without importing scene classes. `Splats` uses it for initialization; `SplatLoader` adapts it to the Three.js loader API. Completion callbacks run before the loading manager ends the item.

`RadSource` and `SogSource` share reads, request settings, and cancellation through `loaders/source.js`. Companion-file resolvers run on the calling thread, and caller-owned buffers are copied before transfer. See [SplatLoader](SplatLoader.md) for the public loading API.

## Post-decode boundaries

The [postDecode](PostDecode.md) API builds expressions on the calling thread and executes them in decode workers:

| Module | Responsibility |
| --- | --- |
| `program.js` / `builder.js` | Public API, program identity, typed expressions, and patch validation |
| `protocol.js` | Opcodes, packed layouts, and shared types without builder or runtime dependencies |
| `optimizer.js` | Fusion of single-use arithmetic intermediates before compilation |
| `compiler.js` | Conditional flow, dependencies, packed instructions, and attribute snapshots |
| `registers.js` | Runtime register allocation and values carried between condition stages |
| `operations.js` / `runtime.js` | Packed input reads, block execution, conditions, and output writes |

Decode workers import runtime and protocol modules directly, keeping expression construction and compilation outside their dependency graph.

## Shared streaming boundaries

Loaders own transport and parsing; schedulers own selection, fades, publication, and retirement.

- `StreamWorkerPool.run()` queues worker leases, assigns task IDs, links cancellation, counts downloads, and balances loading-manager notifications. Each loader has its own pool; format-specific callbacks retain SOG caches or release RAD decoder slots.
- `IndexedSplats` shares texture storage and selected-index reads between `RadPagedSplats` and `SogRegionSplats`. Slot assignment and scene attachment remain with the format-specific scheduler and batch classes.
- `StreamCameras.js` owns the registered cameras and their resolutions, and expands a WebXR `ArrayCamera` into its eye views once they have a projection and viewport.
- `streamOptions.js` owns shared defaults, validation, retry classification, and statistics. `StreamByteBudget` bounds pending copies separately from active loads; ready data has no per-update byte allowance.

`splatBudget` controls selected detail, not total memory. Resident-byte estimates exclude pending copies and WASM memory, which are reported separately; resident storage has no byte cap. Pending copies allow 8 MiB per concurrent load (32 MiB by default), enlarged for an indivisible RAD page; one oversized item can proceed alone. This bounds the waiting queue, not the bytes published or uploaded per frame.

Applications must keep calling `update()` while waiting for `firstRenderable` and while loading, fades, retries, or retirement need to advance. `onChange` requests redraws; it does not drive scheduler updates. Schedulers update ordinary camera matrices, but read a WebXR camera's eye matrices directly and select detail for each eye. Streaming updates before rendering may use the previous frame's XR pose.

## Streamed SOG boundaries

[SogStreamScheduler](SogStreamScheduler.md) loads `lod-meta.json` scenes. Ordinary `.sog` files and `meta.json` use the regular model loader.

- `sogLod.js` parses manifests and selects LOD targets using `splatBudget`. `SogVisibility` keeps the spatial tree and distance-based priorities in the LOD worker.
- `SogStreamLoader` owns the LOD worker, decoding pool, and cached chunk sources.
- `SogStreamBatch` owns occupied slots and mesh attachment; `SogRegionSplats` owns indexed region data.
- `SogStreamScheduler` owns per-region targets, pending extractions, current/outgoing regions, fades, and retirement. It reuses cached detail and refines large gaps gradually. Each region finishes its current crossfade before admitting another LOD.

SOG retains resources per chunk and region:

| State | Owned resources and release point |
| --- | --- |
| Chunk load | Abort controller and loading slot remain until the request settles; successful decoding retains a worker cache handle |
| Cached chunk | Decoded worker data and its worker lease remain while wanted, loading, or needed by visible/fading regions or pending extractions; otherwise they release after `cooldownMs` milliseconds |
| Pending extraction | Target range, chunk reference, and reserved bytes remain until extraction settles; stale results are discarded |
| Ready region | Copied records and pending bytes remain until upload writes them into a batch slot or a target change discards them |
| Current region | Batch slot and opacity state remain while visible or fading; a hidden region releases after cooldown once no outgoing region remains |
| Outgoing region | Previous LOD slot remains until its fade-out finishes, then releases immediately |
| Batch storage | A chunk's shared mesh and source storage remain while any region slots are occupied; releasing the last slot disposes both |

Pending extractions keep their chunk cache referenced, even if the target changes before the reply arrives. Replies are accepted only while the scheduler is alive and the pending region still matches the target. Disposal stops workers, releases chunk caches and region slots, and clears pending state.

## RAD boundaries

[RadStreamScheduler](RadStreamScheduler.md) loads RAD scenes with a LOD tree. Ordinary RAD loading validates the full tree and extracts leaves before applying `postDecode`.

- `RadSource` owns bounded reads, HTTP Range consistency, companion-page resolution, and cancellation.
- `RadStreamLoader` owns a dedicated LOD worker and a bounded decoding pool. Packed geometry transfers to the calling thread; tree arrays transfer to the LOD worker. Decoder slots release after decoding, while pending-byte reservations remain until tree registration and publication can complete.
- `rad_lod.rs` selects a camera-dependent tree cut using file-global node indices. Children replace parents only as complete groups. `radFade.js` compares selections and prepares transitions in the LOD worker.
- The LOD worker retains each chunk's inverse Morton order and block bounds until chunk release. `prepareRadSelection.js` builds render indices and merges current/post-fade bounds together; publication and fade completion switch indices and bounds together on the calling thread.
- `RadStreamScheduler` owns page requests, slot occupancy, publication, fades, retries, and retirement. `RadPagedSplats` and `RadStreamBatch` own page storage and selected-index data. Shared nodes render once, and at most two selections overlap during a fade.

The scheduler retains resources through these stages:

| State | Owned resources and release point |
| --- | --- |
| Page load | Abort controller, phase, and reserved bytes remain until the load settles, including after cancellation |
| Decoded page | Packed buffers and an optional reserved pool slot remain until writing creates resident storage and drops the buffers |
| Resident page | Pool and slot remain allocated until retirement clears both the page allocation and slot entry |
| Traversal | Snapshot page pins, previous cut, and requested budget remain until traversal settles |
| Ready cut | Selection and page pins are consumed on publication or released on invalidation |
| Preparation | Pool snapshots, page pins, and pending bytes remain until the result is consumed or discarded; cancellation prevents publication |
| Displayed cut | Selection, protected pages, and fade state are replaced together on publication or cleared when hidden |

Page pins prevent retirement while traversal, preparation, or display still needs the data. They do not renew cooldowns. Unused pages retire during cleanup after fade-out and `cooldownMs` milliseconds; empty pools release their storage. Root and traversal ancestors remain available for coarsening. Decode generations prevent stale cancellation from releasing replacement pages.

Budget changes invalidate pending selections while preserving the displayed cut. Hiding clears the displayed cut and wanted pages. Disposal terminates workers before dropping their snapshots and page pools.

Both schedulers defer expired-cache retirement while a new LOD decision is pending, preserving the original expiry times. Each accepted decision updates wanted data before cleanup, allowing cache reuse after an update pause and regular retirement during continuous camera movement. SOG also protects newly selected regions before their opacity recovers. Hidden scenes can continue cleanup without waiting for a new selection; existing resource pins still apply.

`SplatOpacityTable` separates source-block group IDs from opacity coefficients. SOG regions fade independently; RAD uses stable, incoming, and outgoing groups. Fade ticks change coefficients without rewriting source records or picking opacity.

## Imports and extensions

- Applications import from `gaussian-splat-lite`, including `utils` and `defines`; source paths are internal.
- Internal modules import helpers from their owner. `utils/index.js` is the public entry point.
- Keep scene updates and sorting handoffs in shared rendering code, with backend-specific storage and output handling in each backend.
- Keep options and types beside their owner. Shared uniform defaults must not import backends; native projected-cache layouts belong in `webgpu/`, separately from packed source layouts in `data/`.
- Keep numeric codecs separate from Three.js object unpacking so decode workers avoid scene dependencies.
